# Phoenix scout report (HEAD `e127482`)

## 1. Module map and product surfaces

### Platform/server (`src/phoenix/`)

- `src/phoenix/server/app.py` composes the FastAPI application, middleware, auth, static UI, OpenAPI, GraphQL, v1 REST, OTLP/gRPC ingestion, background daemons, database insertion, sandbox runtime, in-process MCP, PXI agent MCP, and optional docs MCP. `src/phoenix/server/main.py` exposes `phoenix serve`, `db`, and `datagen` CLI subcommands; root `pyproject.toml` maps both `phoenix` and `arize-phoenix` scripts here.
- `src/phoenix/server/grpc_server.py`, `src/phoenix/trace/otel.py`, and `src/phoenix/trace/span_json_decoder.py` are the ingestion/normalization path. `src/phoenix/db/` contains engines, migrations, models, bulk insertion, trace/span/dataset/annotation persistence.
- `src/phoenix/server/api/schema.py`, `queries.py`, `subscriptions.py`, `mutations/`, `types/`, and `routers/v1/` provide GraphQL and REST contracts. v1 router modules include `traces.py`, `spans.py`, `sessions.py`, `datasets.py`, `experiments.py`, `experiment_runs.py`, `experiment_evaluations.py`, `annotations.py`, `prompts.py`, `projects.py`, and related annotation/config routes.
- `src/phoenix/server/daemons/` includes experiment runner/sweeper, agent-session sweeper, span cost calculator, retention/data sweepers, DB monitoring, and generative-model/system-settings stores. `src/phoenix/server/mcp_server.py`, `mcp_code_mode.py`, and `server/mcp/skills/` implement remote MCP/code mode/PXI skills; `server/sandbox/` hosts code-execution backends. These are platform concerns, not required for the local Styrir skill.
- Other top-level core areas are `src/phoenix/trace/` (normalized traces and local datasets/evaluations), `src/phoenix/session/` (notebook/process/thread session wrapper), `src/phoenix/datasets/`, `src/phoenix/metrics/`, `src/phoenix/experimental/`, `src/phoenix/config.py`, `settings.py`, `auth.py`, and `utilities/`.

### Trace and evaluation model

- `src/phoenix/trace/schemas.py` defines immutable normalized spans. `SpanContext` has hexadecimal `trace_id`/`span_id`; `Span` has name, span kind, parent ID, start/end timestamps, status (`UNSET`, `OK`, `ERROR`) and message, arbitrary flattened attributes, events, and optional conversation attributes. `SpanEvent` is a timestamped structured log; `SpanException` records exception attributes. `SpanIOValue` carries a string plus MIME type; `TokenUsage` tracks prompt/completion counts; computed fields include latency and cumulative token/error counts.
- `SpanKind` covers `TOOL`, `CHAIN`, `LLM`, `PROMPT`, `RETRIEVER`, `EMBEDDING`, `AGENT`, `RERANKER`, `EVALUATOR`, `GUARDRAIL`, and `UNKNOWN`. The model is OTel-compatible while applying OpenInference semantic names for LLM prompts/completions, retrieval documents, tools, sessions, MIME values, and project resources.
- JSON encoders/decoders (`span_json_encoder.py`, `span_json_decoder.py`) preserve IDs, enums, timing, parent graph, attributes, events, conversation ID, and numpy-compatible values. `trace_dataset.py` flattens/unflattens span attributes into DataFrames/parquet; `span_evaluations.py` stores span/document/trace evaluation tables keyed by span/trace IDs, with score/label/explanation columns and metadata.
- `packages/phoenix-otel/src/phoenix/otel/otel.py` exposes `register()` with endpoint/project/batch/global-provider/headers/protocol/API-key options; `settings.py` resolves `PHOENIX_*` and OTLP settings via nearest `.env.phoenix`, with process environment precedence and checks against mixing endpoint/credential tiers. `__init__.py` re-exports OpenInference context helpers (`using_session`, `using_attributes`, metadata/tags/user/prompt-template helpers) and span-kind/MIME constants.
- `packages/phoenix-client/src/phoenix/client/resources/sessions/__init__.py` models one session as traces grouped by a user session ID; each experimental `SessionTurn` is one chronological trace and extracts input/output from the root span's `input.value`/`output.value` OpenInference attrs. Session annotations accept `LLM`, `CODE`, or `HUMAN` plus score/label/explanation/metadata/identifier. This is a useful conceptual bridge but assumes an OTel trace/root-span source.

### Evals and datasets/experiments

- `packages/phoenix-evals/src/phoenix/evals/` contains evaluator core (`evaluators.py`), execution (`executors.py`), LLM provider adapters (`llm/wrapper.py`, `llm/adapters/{openai,anthropic,google,litellm,langchain}`), prompt templating, tracing, rate limiters, and generated classification configs.
- `packages/phoenix-client/src/phoenix/client/resources/datasets/` supports dictionary/DataFrame/CSV/JSON uploads, input/output/metadata/split/span-ID fields, pagination, complete version snapshots, append/update behavior, and immutable dataset versions. `resources/experiments/` creates/runs/resumes/evaluates experiments, logs runs/evaluations, paginates results, and links each run to an example, repetition, optional output/error, timing, and optional trace ID. Experiments are intended to compare prompt/LLM/retrieval/application variants over identical inputs.
- `packages/phoenix-client/src/phoenix/client/resources/experiments/types.py` accepts evaluator functions over named `input`, `output`, `expected`/`reference`, `metadata`, `example`, and `trace_id`; `ExperimentEvaluationRun` stores either a result or an error and carries evaluator name, annotator kind, timing, metadata, and trace ID. `experiments/evaluators.py` wraps sync/async functions and Phoenix eval `Score` objects; default result conversion supports scores, booleans, numbers, labels, tuples, and result dictionaries.
- `resources/spans/` and `resources/traces/` query spans/traces by project, time, root, session, attributes, IDs, errors, and latency, and add annotations with `LLM`/`CODE`/`HUMAN` kinds. `resources/sessions/` adds ordered turns and session-level annotations. `resources/prompts/` handles prompt versions/invocation; `resources/projects/` handles project metadata.

### Evals taxonomy and check catalog

`packages/phoenix-evals/src/phoenix/evals/metrics/__init__.py` exports 17 built-ins. The specialized classification metrics are LLM-judge evaluators (all subclass `ClassificationEvaluator` in `evaluators.py` and use generated prompt configs):

- **Grounding/answer quality:** `HallucinationEvaluator` (`hallucinated=1`, `grounded=0`, minimize; judges the latest response against the complete prior record including turns, tool calls/results, and read/retrieved content), `FaithfulnessEvaluator` (`faithful`/`unfaithful`, maximize; output vs context), `CorrectnessEvaluator` (`correct`/`incorrect`, maximize), and `CompletenessEvaluator` (`complete`/`incomplete`, maximize; enumerates every active user request as fulfilled, withdrawn, or unfulfilled with pending/blocked/failed/ignored reasons).
- **Retrieval:** `RetrievalRelevanceEvaluator` (`relevant`/`irrelevant`, maximize; external vector/tool/MCP/web/DB information against the request) and deprecated `DocumentRelevanceEvaluator` (`relevant`/`unrelated`, maximize; one document vs question).
- **Conversation/safety:** `ConcisenessEvaluator` (`concise`/`verbose`, maximize), `RefusalEvaluator` (`refused`/`answered`, neutral), `ToxicityEvaluator` (`toxic`/`non-toxic`, minimize), `PiiDetectionEvaluator` (`pii_detected`/`no_pii_detected`, minimize; enumerates findings and source), and `UserFrictionEvaluator` (`friction`/`no_friction`, minimize; latest user message vs preceding assistant behavior).
- **Agent/tool behavior:** `ToolSelectionEvaluator` (correct/incorrect tool choice, maximize), `ToolInvocationEvaluator` (arguments/format/types/required fields/extras/safety, maximize), and `ToolResponseHandlingEvaluator` (error handling, extraction/transformation, retries, disclosure, and use of all results, maximize). The configs explicitly separate selection from invocation and response handling.
- **Code/heuristic metrics:** `exact_match.py` is an exact string equality check with no normalization; `matches_regex.py` checks regex matches; `precision_recall.py` provides precision, recall, and F-beta over expected/output label sequences with macro/micro/weighted averaging, positive-label, beta, and zero-division controls. `create_evaluator(kind="code")` supports arbitrary deterministic functions; `create_evaluator` also supports LLM/custom sources and `KindType` includes `human`, `llm`, `heuristic`, and `code`.
- **Result contract:** `Score` carries `name`, numeric `score`, `label`, `explanation`, metadata, `kind`, and optimization `direction` (`maximize`, `minimize`, or `neutral`). Evaluators validate/bind input schemas, expose descriptions, trace evaluator spans, and inject trace IDs into score metadata. `evaluate_dataframe`/async runs evaluator×row jobs with bounded executors, retries, progress, execution details, and failure reporting. LLM wrappers support multiple providers and text/object/classification generation, with prompt role normalization and tracing.
- **Prompt-specific coding-agent relevance:** `prompts/classification_evaluator_configs/COMPLETENESS...yaml` explicitly models active requests and pending/blocked/failed/ignored outcomes; `HALLUCINATION...yaml` includes tool calls/results and prior conversation; `RETRIEVAL_RELEVANCE...yaml` includes MCP/tool/web/database retrieval; tool YAMLs distinguish selected tool, invocation correctness, and response handling. These are useful rubric ideas, not code to copy.

### PXI and Harbor eval harnesses

- `evals/pxi/online_evals/` contains target-span selectors, topology/conversation hydration, provider judging, and annotation rendering. `OVERVIEW.md` documents one conversational turn per trace, root `pxi.turn` (`AGENT`) plus model/tool/subagent spans, structured approval markers, a five-minute settle delay, `(span_id,name,identifier)` checkpoints, overlap self-healing, deterministic SHA-256 trace sampling, ≤8 evaluation concurrency, ≤100 annotation batches, a 5,000 discovery cap, and per-target error handling. These assumptions are PXI-specific but the operational invariants transfer.
- `evals/pxi/harness/run_experiment.py` runs dataset tasks, performs health checks, records metadata/Git identity, uploads/executes experiments, and fails loudly on missing evaluations. `harness/reporting.py` builds pure local reports: full-fidelity `<stem>.report.json` and bounded `<stem>.report.md`, with experiment/trace links, stable example IDs, model/provider/Git/split metadata, task/evaluator errors, tool calls, input/expected/actual output, repro commands, and static-prompt collapsing. `gate.py` validates schema/session/recording health, resolves split/override threshold policy, excludes infra errors from behavioral denominators, retries clean misses/task errors up to `RETRY_FAILED_CAP=15`, reconciles row keys, and distinguishes pass/flaky/tolerated/retry-required/regression/too-many-failures/unmeasurable.
- `evals/harbor/` and `packages/phoenix-client/src/phoenix/client/harbor/` map Harbor task collection→dataset version, task→example, agent/model config→experiment slice, attempt→repetition, terminal trial→experiment run, verifier reward→CODE evaluation, infra exceptions→run error plus `infra_ok=0`, and ATIF trajectory→trace/session. The plugin uses canonical SHA-256 identity (job/config/task digests), complete dataset snapshots, immutable creation-time version pinning, terminal non-retried attempts, run reuse checks, conflict recovery, and best-effort ATIF trace conversion. `evals/harbor/tasks/regression-triage/` demonstrates a multi-step task with deterministic SQLite fixtures and persisted cross-step headless-agent state.

## 3. Borrow list: ideas/patterns versus copy-code

### Safe architectural ideas to reimplement independently

1. **Normalized event/span graph:** retain stable run/session/turn/event IDs, parent-child relationships, start/end/status, typed stage/kind, input/output MIME, structured attributes, exceptions, and provenance. Map OTel/OpenInference concepts where useful, but make the local schema file-log-native.
2. **Session and turn grouping:** a session groups ordered turns; each turn can carry user input, agent output, tools, model calls, nested agents, and evidence. Phoenix's root-span IO extraction is a useful shape, but Styrir must not require a root OTel span.
3. **Evaluator contract:** define a small result object like `{name, score, label, explanation, metadata, kind, direction}`; distinguish deterministic CODE checks from LLM judges and human review; allow named inputs and structured evidence. Keep scores, errors, and infrastructure health separate.
4. **Code-first quality gates:** use exact/regex/sequence checks for invariants and reserve LLM judges for nuanced completeness, grounding, tool behavior, and friction. The built-in prompt configs are rubric inspiration only.
5. **Immutable evidence snapshots:** represent each ingested session file/run as a content-addressed or digest-addressed immutable snapshot; preserve source path, file hash, parser/version, event count, and timestamps. This is analogous to Phoenix dataset versions and Harbor complete snapshots.
6. **Run identity separate from display names:** use provider/session/skill/agent/config/content digests as identity and permit human-readable names to change. Harbor's job/config/task digest model is a strong template.
7. **Experiment/evaluation records:** pin a run to a snapshot and skill/config revision; key repeated attempts by `(snapshot, example/turn, repetition)`; retain output/error/timing/trace/session links; attach evaluator results as separate rows.
8. **Bounded online runner:** borrow the invariants from PXI—settle incomplete inputs, deterministic sampling, bounded concurrency, checkpoints/idempotence, overlap self-healing, batch writes, discovery caps, and per-target failures—without its Phoenix server or `pxi.turn` assumptions.
9. **Two-attempt gate and evidence artifacts:** validate artifact/session health before judging behavior; exclude infra rows from behavioral denominators; retry only bounded clean misses/task failures; reconcile stable row keys; distinguish pass, flaky, tolerated, regression, and unmeasurable. Emit full machine JSON plus bounded Markdown and include repro/source links.
10. **ATIF/Harbor conversion concepts:** preserve turn/step/tool/model chronology, terminal attempt semantics, deterministic IDs, retry exclusion, run reuse immutability, and reward-versus-infrastructure separation. Implement adapters for the target log formats instead of copying `_traces.py`/`_plugin.py`.
11. **Secure local configuration:** the OTEL settings pattern (nearest `.env.phoenix`, process-env precedence, endpoint/credential tier separation, permission/size/trust checks) suggests explicit config precedence and secret-safe local files; implement independently for Styrir.
12. **Agent-facing interfaces:** CLI commands can query sessions, run checks, compare skill revisions, and emit raw JSON; a local MCP/skill interface is optional. Phoenix's remote MCP, GraphQL, and interactive UI are not prerequisites.

### Code/assets to avoid copying

- `src/phoenix/` server/database/GraphQL/UI/playground/MCP/PXI implementation and the root package as a whole: ELv2 and substantially tied to the hosted platform.
- `packages/phoenix-evals` implementation and exact classification YAML prompt text: package ELv2. Recreate coding-agent rubrics from observed behavior and cite provenance internally rather than transplanting files.
- Phoenix-specific LLM-app instrumentation/autoinstrumentation/provider adapters, retrieval-document conventions, token/cost accounting, playground/span replay, and remote API plumbing: useful for LLM application traces but mostly not the local session-file problem.
- Harbor/PXI implementation files themselves: even where their package metadata is Apache, they embed Phoenix API/data contracts and are unnecessary coupling. Reimplement the small identity/state/reporting invariants.
- Any dependency/vendor code without a separate license audit.

## 5. Proof gaps and boundaries

- This was a source/module/metadata inspection only. No Phoenix server was started, no live OTLP/API/MCP request was made, and no evaluator or Harbor run was executed; runtime behavior is therefore not independently verified here.
- Per the scout constraint, formatters, linters, project-wide tests, builds, and package-manager actions were not run.
- `src/phoenix/` was mapped at module level rather than exhaustively reading every server/database/UI implementation; the report intentionally omits incidental internals.
- The Python OTEL/client `IP_NOTICE` versus Apache metadata/LICENSE conflict is observed, not legally resolved. A legal owner must decide before any source reuse.
- JS license conclusions are based on package metadata and the license files observed by repository glob; this is not a complete transitive dependency/SBOM audit.
- “No generic adapter” and other gap statements mean no such surface was found in the requested inspected paths; they are not claims that no related integration exists anywhere in the repository or upstream ecosystem.
- Recommendations in the borrow/gap sections are implications for the Styrir design, not Phoenix product claims.
